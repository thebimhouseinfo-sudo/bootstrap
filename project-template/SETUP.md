# Bootstrap project setup — runtime-neutral

**Recommended first-time setup:** `install.py --staged` (preview first, then `--apply` after human approval). This installs a BOOTSTRAPPING lifecycle marker before hooks can enforce write blocking. Legacy installations without staged marker retain their existing behavior. Follow `harness/common/setup_lifecycle.py audit`, `smoke`, `host-test`, fresh real-host verification in a disposable workspace, explicit Human-terminal `activate --evidence ...`, then fresh post-lock verification and Human-terminal `finalize --post-lock-evidence ...` after a second specific decision. The deprecated `--human-approved` flag is not authentication. Only `HANDOFF_COMPLETE` permits closing the setup tab. Local JSON evidence is manual coordination, not verified human authentication. Never close the setup tab until post-lock tests and handoff complete. Hooks can still be subject to host-level controls regardless of this script marker.

**Two starting points:** new project begins Planner brainstorming and CRITERIA draft; existing project begins verified codebase inspection, matching against existing CRITERIA, then human discussion of desired behavior. Source code is evidence of CURRENT behavior, not human-approved DESIRED requirements. Both then follow the same main path (AGENTS.md) without approval stops between steps: Criteria (existing Criteria: keep or edit, then continue) → Plan with technical direction → Milestones → project-specific Coder/Tester skills and knowledge → whole-Plan Technical Proposal → top-down Critic CR until PASS → audit, smoke and lock → code. The environment architect is not the Product Planner.

**After handoff:** Coder implements the first milestone from the final `docs/TECHNICAL_PROPOSAL.md` (`Critic CR: PASS`); Tester and Reviewer verify each milestone before the next. GOALMAP lives in `docs/IMPLEMENTATION_PLAN.md`, not in CRITERIA.

In Git projects, apply verifies effective ignore behavior before copying setup: nested ignore exceptions produce `LOCAL_SETUP_NOT_IGNORED` and exit 2. Fix those rules before retrying. ## Staged setup status and recovery
`BOOTSTRAPPING`: setup modifications are not blocked by installed project hook adapters; hook enforcement is deferred. `READY`: native-hook configuration activated after audit, disposable positive/negative script smoke and reported live-host observations. `READY_WITH_LIMITATIONS`: Continue/generic clients may have working roles/checks but no native blocking hooks; NEVER claim ENFORCED. `HANDOFF_COMPLETE`: a separate post-lock verification record exists, and the Planner kickoff prompt can be given. `python harness/common/setup_lifecycle.py status` also checks lock-file hashes for drift. `python harness/common/setup_lifecycle.py host-test` prints the keep-setup-tab warning and runtime-specific test instructions. ## Upgrades, interrupted installs, and manual native hook recovery
First successful installs record `harness/.bootstrap-manifest.json` with installed file hashes and chosen tier/runtime. Explicit `install.py --upgrade` may replace an unchanged manifest-owned file, never an independently modified target file. Tier/runtime changes are blocked as MIGRATION_REQUIRED because mixing old/new role or hook adapters is unsafe. There is no automatic code migration; old installs without a manifest require manual reconciliation. Copy failures attempt a content-aware rollback; any leftover path is named for Human review. `python harness/common/recover.py --runtime codex inspect` (or claude/antigravity) reports the native config, and `disable` / `restore --backup BACKUP_ID` are human-operated terminal actions that preserve a backup. Recover to fix broken native hook registration, restart the client, and redo fresh-session positive/negative smoke before relocking. TTY input is not an authenticated Human identity proof.
