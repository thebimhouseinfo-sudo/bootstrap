# Bootstrap project setup — runtime-neutral

**Recommended first-time setup:** `install.py --staged` (preview first, then `--apply` after human approval). This installs a BOOTSTRAPPING lifecycle marker before hooks can enforce write blocking. Legacy installations without staged marker retain their existing behavior. Follow `harness/common/setup_lifecycle.py audit`, `smoke`, `host-test`, fresh real-host verification in a disposable workspace, explicit `activate --evidence ... --human-approved`, then fresh post-lock verification and `finalize --post-lock-evidence ... --human-approved` after a second specific human decision. Only `HANDOFF_COMPLETE` permits closing the setup tab. Local JSON evidence is manual coordination, not verified human authentication. Never close the setup tab until post-lock tests and handoff complete. Hooks can still be subject to host-level controls regardless of this script marker.

**Two starting points:** new project begins Planner brainstorming and CRITERIA draft; existing project begins verified codebase inspection, matching against existing CRITERIA, then human discussion of desired behavior. Source code is evidence of CURRENT behavior, not human-approved DESIRED requirements. CRITERIA approval precedes stack/architecture/refactor proposal; technical approval precedes coder/tester skills, audit and smoke. The environment architect is not the Product Planner.

**After handoff:** invoke Planner to read approved CRITERIA, ARCHITECTURE, PROJECT_PROFILE and source; create/revise `docs/IMPLEMENTATION_PLAN.md` with GOALMAP (every Plan item starts with observable GOAL and CRITERIA references), then propose `docs/MILESTONES.md`. Human approves the Plan/milestones before task assignment. GOALMAP does not live in CRITERIA.



AI installs from repo root using `python install.py --target PATH --tier Standard --runtime RUNTIME --apply` **after explicitly choosing one of antigravity/codex/claude/continue/generic (generic additionally requires --target-app), preview and user approval**. This copies only missing files; it does not overwrite existing work. A conflicting `AGENTS.md` produces `AGENTS.bootstrap.md` for manual reconciliation, and exit 2 means unresolved conflict.

**Git mode local/tracked:** the installer also manages a marked block at the end of the target `.gitignore`, preserving existing rules. Agent directories, harness/runtime state, local AGENTS/CLAUDE/TASKS, project environment profile, generated trace and report templates stay local. Product source and actual product docs remain trackable. Preview lists `UPDATE .gitignore`; apply atomically updates that managed content. Already tracked setup is reported as `TRACKED_LOCAL_SETUP` with exit 2; ignore rules cannot untrack it. Do not automatically delete files, rewrite history or remove index entries. The canonical `project-template/` in bootstrap remains versioned source.

In Git projects, apply verifies effective ignore behavior before copying setup: nested ignore exceptions produce `LOCAL_SETUP_NOT_IGNORED` and exit 2. Fix those rules before retrying. Git access/index errors block rather than pretending the repository is absent. If Git is unavailable or the project has not been initialized, rerun after `git init` to validate real ignore behavior.

## Google Antigravity IDE setup
Install with `python install.py --target PATH --tier Standard --runtime antigravity --apply` (or use `--ask-first` for interactive pre-ask configuration). The installer configures native `.agents/hooks.json` (Stop lifecycle hook dispatching to `harness/common/verify.py`), `.antigravity/agents/*.md` (role definitions with model assignments and Gemini 3.8 Flash High fallback), and native `.agents/skills/`.

**After install:** open the workspace in Google Antigravity IDE. Roles, skills, and hooks are loaded natively. Run `python harness/common/status.py --tier Standard --runtime antigravity` to inspect inventory and readiness; configure `harness/common/checks.json` with verified project build/test commands.

## Codex setup
Install with `--runtime codex`. Inspect `/hooks` inside Codex and trust the exact definitions if approved. Configure actual project commands in `harness/common/checks.json` and an explicitly approved `harness/active-task.json`; no fabricated goal ID. Stop checks activate for configured tasks only.

## Claude Code setup
Install with `--runtime claude`. The installer copies `.claude/settings.json` (with `UserPromptSubmit`, `PreToolUse`, `Stop` hooks), `.claude/agents/*.md` subagent files, and `harness/claude/hook.py` (the Python adapter). The adapter reuses `harness/common/*.py` and reads native `hook_event_name` from JSON stdin; exit 2 blocks supported events. Hook commands locate the adapter from project root or nested directories.

**After install:** open the project in Claude Code, check that the hook fires on prompt submit (context message appears). Run `python harness/common/status.py --tier Standard --runtime claude`; configure `harness/common/checks.json` with real build/test commands; set branch authority if using Git. Save real host/client/version, exact source hashes and observed hook/block/Stop evidence. Do not clear readiness blockers by editing capability labels; Standard engines remain NOT_CONFIGURED until implemented and verified.

## Cross-runtime generic readiness (not gate-engine readiness)

**Purpose:** minimize setup quota and time. Copy reusable agent contracts and native files first, configure only the specific project and any genuinely missing host adaptation.

- **Codex and Google Antigravity IDE: GENERIC READY**, installed and tested; no generic template rewrite needed merely to use them. These applications are equally supported; neither is the primary runtime.
- **Claude Code: CONFIGURED, HOST-UNTESTED**; prepared files can be installed without regenerating them, but Claude Code has not been verified for an observed host test.
- **Continue: NEAR GENERIC READY, HOST-UNTESTED**; role definitions/configs exist, but selecting actual provider/model mappings and verifying Continue-specific runtime behavior is necessary. VS Code similarity with Antigravity is not proof of API equivalence.
- **Other coding agents:** modify/carry over the template's native adapters and paths according to the agent's platform. Reuse common role/skill procedures, not a newly generated harness.

After installation, all target projects still need project-specific CRITERIA, host/stack/SDK, build/test commands and relevant Git/model/knowledge configuration. This generic READY label is separate from `RUNTIME_VERIFIED`, authenticated approvals and `ENFORCED` protections. Installer copy/CI tests alone do not prove those stronger properties.

## One-batch installer intake

Run `python install.py --ask-first` to **display all questions as one noninteractive block** for the AI to ask in chat. This command NEVER changes files and cannot be combined with `--apply`. After Human answers once, pass explicit `--target`, `--tier`, `--runtime` and, if generic, `--target-app`. Run a preview without `--apply`; only after Human approves it, rerun with `--apply`. The installer does not ask step-by-step questions in a terminal; host command execution permission dialogs remain separate from chat configuration questions.

## Staged setup status and recovery
`BOOTSTRAPPING`: setup modifications are not blocked by installed project hook adapters; hook enforcement is deferred. `READY`: native-hook configuration activated after audit, disposable positive/negative script smoke and reported live-host observations. `READY_WITH_LIMITATIONS`: Continue/generic clients may have working roles/checks but no native blocking hooks; NEVER claim ENFORCED. `HANDOFF_COMPLETE`: a separate post-lock verification record exists, and the Planner kickoff prompt can be given. `python harness/common/setup_lifecycle.py status` also checks lock-file hashes for drift. `python harness/common/setup_lifecycle.py host-test` prints the keep-setup-tab warning and runtime-specific test instructions. Retain independently accessible offline recovery if project-local scripts become unusable. Never reinterpret a fixture/log as independently authenticated approval.

## Upgrades, interrupted installs, and manual native hook recovery
First successful installs record `harness/.bootstrap-manifest.json` with installed file hashes and chosen tier/runtime. Explicit `install.py --upgrade` may replace an unchanged manifest-owned file, never an independently modified target file. There is no automatic code migration; old installs without a manifest require manual reconciliation. Copy failures attempt a content-aware rollback; any leftover path is named for Human review. `python harness/common/recover.py --runtime codex inspect` (or claude/antigravity) reports the native config, and `disable` / `restore --backup BACKUP_ID` are human-operated terminal actions that preserve a backup. Recover to fix broken native hook registration, restart the client, and redo fresh-session positive/negative smoke before relocking. TTY input is not an authenticated Human identity proof.
